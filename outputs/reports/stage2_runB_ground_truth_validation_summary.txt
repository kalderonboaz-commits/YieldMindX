------------------------------------------------------------------
IMPORTANT INTERPRETATION
------------------------------------------------------------------

How much of the known synthetic relationship structure did LightGBM recover
blindly? Strictly, very little (1/9 exact); allowing close, well-justified
proxies, still modest (2/9 practical). This is an honest, not-inflated result.

Which relationship types LightGBM handled well:
  - Threshold-type relationships in DOMINANT, high-signal feature families
    (the leakage-current family) were found cleanly, confidently, and
    stably -- relationship #6 is the clearest success.
  - When a parameter (or a close correlated sibling) has genuine importance,
    threshold/negative shapes are reliably characterized with strong
    fold-stability (#3 via proxy).

Which relationship types LightGBM missed or could not test:
  - Symmetric, non-monotonic effects (a true U-shape with near-zero net
    linear correlation) received LITERALLY ZERO importance from the fitted
    model in this run (#1, and the Rc/TOPSIN_Gm_max components of #5/#8) --
    not merely excluded by screening, but never used by the full model at
    all. This is the clearest capability gap.
  - 2-way and 3-way interactions where one or more legs have low-to-zero
    marginal importance were never tested, because interaction search here
    only covers the 50-feature candidate pool (#4, #5, #9).
  - A genuine 3-way interaction has no dedicated search method in this
    pipeline at all -- it is structurally undetectable regardless of
    candidate coverage (#9).
  - A derived cross-stage delta, with engineered features excluded by
    design, could only be reconstructed via an implicit two-feature
    interaction -- which requires BOTH raw features to have real
    importance; here one did not (#8).

Did candidate-pool screening exclude important planted relationships?
  Yes, demonstrably -- checked directly against the frozen pool file, not
  inferred: SIN_Thickness_SiN_Thickness, GATE2_Ali_Litho_Gate_to_recess_
  alignment, TOPSIN_ET_DC_PIV_Drain_Lag_1 (exact column), and
  TOPSIN_ET_Load_Pull_P.A.E_Last (for interaction purposes) never entered
  the 154-feature screening set or 50-feature candidate pool, despite two
  of these (Alignment, Drain_Lag_1's proxy) having real underlying signal.

Main limitation -- model capability, candidate coverage, explainability
method, engineered-feature exclusion, or a combination?
  A COMBINATION, with different relationships failing for different,
  specific, verified reasons:
  - MODEL CAPABILITY is the root cause for #1 (Gate CD) and the Rc/TOPSIN_Gm_max
    legs of #5/#8: LightGBM assigned these features EXACTLY ZERO importance
    across the full 1,425-feature fit -- no downstream method could have
    recovered them without a different model or explicit feature engineering.
  - CANDIDATE/SCREENING COVERAGE is the root cause for #4, #7, and the
    interaction-testing gap in #3: real signal existed but fell outside the
    ~150/50-feature thresholds used for deeper analysis.
  - EXPLAINABILITY METHOD (the simple PDP-shape heuristic) is implicated in
    #2: real importance was detected, but the shape classifier called it
    "flat" -- a more sensitive or differently-parameterized shape method
    might recover it.
  - PAIRWISE-ONLY INTERACTION SEARCH is a structural, unconditional
    limitation for #9 regardless of any other fix.
  - ENGINEERED-FEATURE EXCLUSION (by design, per this project's Stage 2
    scope rule) compounds with the TOPSIN_ET_Gm_max capability gap to make
    #8 unrecoverable under the current design.

No single fix addresses all nine misses/gaps -- they are genuinely
heterogeneous failure modes, and this validation report distinguishes them
rather than lumping them into one general "needs more work" conclusion.
